# Requirements Document

## Introduction

The Customer Response Loop closes the one side of Revora that is currently open: the customer's. Revora already detects a failed payment, diagnoses it from the provider's own error fields, prices every candidate action, ranks by net recovery value, gates every external effect behind a deterministic Policy_Engine, executes exactly once, and declares recovery only from an authoritative provider read. What it cannot do is hear back. It never learns that the money is coming on Friday, that the card was replaced, that the amount is too high this month, or that the customer disputes the charge outright — so every decision cycle after the first re-decides on the same stale evidence the first one had.

This feature adds a public, single-case, token-scoped page where a customer states why the payment is late and, optionally, when they will pay; activates `PROMISE_TO_PAY_FOLLOW_UP` as a real executable action; feeds customer-stated reasons into diagnosis and Recovery_Memory without letting them touch policy; builds the bounded Gemini-backed Reasoning_Adapter the base design always permitted but which was never implemented; renders a per-case stage timeline over the existing gap-free audit trail so a reader can follow one case end to end; and produces demonstration evidence adequate to the hackathon bar — verified money recovered across a batch, and a completed experiment with a real uncertainty interval rather than an empty page.

It also closes a second defect found while verifying the decision doctrine against the implemented code, one that is independent of the customer surface and more consequential than it looks: a Recovery_Case where Revora correctly chose to wait can never be re-decided, because no transition edge exists out of POLICY_CHECK back into DECISION_PENDING. Requirement 30 adds that edge together with a scheduled review, an event-driven review, and a customer-signal-driven review. Requirement 31 splits the blended `action_cost` into a financial cost and a communication cost so that an exclusion on cost grounds names which cost caused it.

**This is an additive spec.** It layers on `.kiro/specs/revora-incremental-revenue-recovery/`, which is already implemented. It restates nothing from that document. Where it touches an existing requirement it says so by reference in the form `R11.C4` (Requirement 11, acceptance criterion 4). Requirement numbering continues at 18 and correctness-property numbering continues at P31, so a reference is unambiguous across both documents.

**What does not change.** The core principle is unchanged: AI recommendation is not AI authority, and nothing a customer types is authority either. The Policy_Engine keeps exactly the twelve ordered checks of R8.C2 — this feature adds no thirteenth check. Recovery keeps exactly one definition: the full at-risk amount, captured, confirmed by an authoritative provider read (R10.C1). The Recovery_Window is still set once at case creation and never extended (R2.C5), which is what makes termination provable. Every currency figure is still an integer count of minor currency units (R7.C12); no requirement in this document introduces a fractional or floating-point currency value.

### Evidence Discipline Used In This Document

The tags carry the same meaning as in the base spec:

- **[FACT]** — verifiable from the base spec, from the implemented codebase, from the hackathon brief, or from established engineering practice.
- **[ASSUMPTION]** — a working premise chosen to make the requirement testable; confirm or replace during design.
- **[INFERENCE]** — a conclusion derived from stated premises rather than direct evidence.
- **[EVIDENCE INSUFFICIENT]** — unknown at requirements time; verify before design closes. No provider endpoint name, payload shape, statutory claim, or behavioural benchmark has been invented to fill a gap.

One provider capability is load-bearing and unverified: whether the Payment_Provider exposes a way to re-notify a customer about an already-created payment link without creating a second link. Requirement 24 is written against a generic capability so a verified alternative substitutes without rewriting the requirement. **[EVIDENCE INSUFFICIENT]**

### Deployment Assumption — Recorded Because The User Did Not Answer

**[ASSUMPTION]** The React frontend deploys to Vercel; the FastAPI application and the worker deploy to a container host that supports a long-lived process and a sub-minute scheduler (Render, Railway, or Fly). Three reasons, stated so the assumption can be argued with rather than inherited:

1. The worker is a long-lived poll loop, not a request handler. A function runtime terminates it.
2. Six periodic sweeps exist (lifecycle evaluation, execution reconciliation, payment-state reconciliation, detection-gap backfill, calibration report, customer-data retention) and this feature adds two more: promise-follow-up scheduling and the Review_Sweeper of Requirement 30. R17.C11 gives the retention sweep a 24-hour deadline, R24 gives promise follow-up a bound measured in minutes, and R30.C5 gives the review sweep a bound measured in minutes. A once-per-day cron cannot meet any of the three.
3. Webhook signature verification runs over the unmodified raw request bytes (R1.C1). Moving that path to a runtime that re-encodes, re-orders, or buffers the body differently invalidates every signature simultaneously, and the failure presents as universal 401 rather than as a deployment error.

The consequence for this feature specifically: the public customer page is a static React route served from the frontend host, and every read and write it performs crosses to the API host. That makes the API host's CORS configuration and rate limiting part of the customer page's security surface, covered in Requirement 29.

### One Conflict With The Base Spec, And How It Is Resolved

The brief asks for a completed synthetic experiment so that incremental revenue reports a number rather than `NOT_ESTABLISHED`. The base spec forbids exactly that: R13.C12 labels any synthetic-input experiment `SYNTHETIC`, R13.C8 disqualifies a `SYNTHETIC`-labelled experiment from producing `Attributed_Recovery`, and R12.C4 permits `incremental_recovered_revenue` to carry a number only from `Attributed_Recovery`. Weakening any of those three would let generated data underwrite a causal claim about real money, which is the precise failure the base spec was written to prevent.

Requirement 28 resolves it without weakening anything: the synthetic experiment reports a **separate, separately named** figure, `demonstration_incremental_revenue`, carrying its own numeric value, its own uncertainty interval, the `SYNTHETIC` provenance label, and a `DEMONSTRATION_ONLY` label. `incremental_recovered_revenue` continues to report `NOT_ESTABLISHED` until a real-traffic experiment earns a number. The experiments page fills with a real measurement and a real interval; the claim it licenses is "the measurement machinery works", not "we recovered this much of your money".

**Decision recorded and confirmed.** The two-figure split stands as written. No acceptance criterion of Requirement 28 changes, R13.C8 and R13.C12 stay unweakened, and `incremental_recovered_revenue` keeps reporting `NOT_ESTABLISHED` until a real-traffic experiment earns a number.

### Recorded Decision — The Single Permitted Link Is The Customer Response Page (Shape B)

Customer-visible content may contain exactly one link: R4.C7 requires zero links other than the single Policy_Engine-approved link, and the implemented message builder honours that. The customer page adds a second candidate URL, and the two shapes produce materially different recovery behaviour. **Shape B is chosen:** where Revora authors the customer-visible content, the single permitted link is the Customer_Response_Page URL, and the Customer_Response_Page carries the payment link (already required by R19.C1) alongside the reason and promise form.

**Accepted cost.** Paying takes one additional interaction compared with linking straight to payment, and the size of that conversion cost is unmeasured. **[INFERENCE]**

**Why the cost was accepted.** A response page no recipient reaches leaves the customer side of the loop open, which is the single gap this feature exists to close. A shorter path to payment that never yields a Delay_Reason or a Promise_To_Pay returns Revora to re-deciding every cycle on the evidence the first cycle had. **[INFERENCE]**

One exception is recorded rather than hidden: where the external effect is a Payment_Provider notification whose message content the provider authors, Revora does not control which URL that notification carries. R24.C17 records that case explicitly as provider-hosted rather than pretending Shape B holds there.

### Recorded Decision — Implemented Enumerations Are Not Renamed

Recorded so it is not revisited. The implemented enumeration members keep their names:

- `DO_NOTHING` and `WAIT` stay two distinct members. They are not collapsed into one `WAIT_AND_OBSERVE`.
- `CUSTOMER_MESSAGE` is not renamed to `REMINDER`.
- `STOPPED`, `BLOCKED`, and `EXPIRED` stay three distinct Terminal_States. They are not collapsed into one `STOP`.

Two reasons. First, the three-way terminal split is what lets the unresolved-Recovery_Case grouping of R14.C10 distinguish five different problems that hold the same money — a bound exhausted, a policy prohibition, a window elapsed, a human handoff, and an infrastructure failure. Collapsing it destroys a reporting capability the base spec deliberately built. **[INFERENCE]** Second, renaming a persisted enumeration member is a migration plus a change to a stored contract, bought for no behavioural gain. **[FACT]**

What does change is presentation only, covered by R26.C14: the Merchant_Dashboard and the Case_Timeline render `DO_NOTHING` and `WAIT` under a shared human-readable label conveying waiting and observing rather than stopped, and render each of the three Terminal_States under its own distinct human-readable label.

**[FACT]** `RETRY` and `DELAYED_RETRY` stay `UNAVAILABLE`. No Payment_Provider capability exists to retry a failed one-off payment; automatic retry exists only in the provider's subscriptions product, which operates on a different object and is out of scope. Both stay visible in the recorded Candidate_Action set with their exclusion reason under R6.C9 rather than being hidden from the record.

## Glossary

### New Components

- **Customer_Response_Service**: The component that issues and validates Customer_Access_Tokens, serves the Customer_Response_Page read model, and records Customer_Signals. It performs no action selection and no policy evaluation.
- **Customer_Response_Page**: The public, unauthenticated, single-case web page a customer reaches from a Customer_Access_Token URL.
- **Timeline_Reader**: The read-only component that projects the persisted Audit_Records of one Recovery_Case into a Case_Timeline. It owns no table and writes nothing.
- **Reasoning_Adapter**: The concrete implementation of the Reasoning_Layer against the configured model provider. Subject in full to Requirement 4 of the base spec.
- **Demonstration_Loader**: The component that seeds a Demo_Batch and drives a Demonstration_Experiment to a terminal experiment state.
- **Review_Sweeper**: The periodic component that visits every Recovery_Case waiting at POLICY_CHECK whose next_review_at instant has been reached and enqueues exactly one decision cycle for it. It reads persisted timestamps only and owns no queue state.

### New Domain Terms

- **Customer_Access_Token**: A signed, expiring bearer credential scoped to exactly one Recovery_Case, granting read of that Recovery_Case's Customer_Response_Page projection and write of Customer_Signals for that Recovery_Case only.
- **Customer_Signal**: One recorded customer-side submission on one Recovery_Case. Advisory evidence. Never an authorization.
- **Customer_Signal_Kind**: The kind of a Customer_Signal, drawn from PAGE_VIEWED, DELAY_REASON, PROMISE_TO_PAY, PARTIAL_ARRANGEMENT_REQUEST.
- **Delay_Reason**: The customer's stated reason the payment is late, drawn from exactly SALARY_OR_CASHFLOW_TIMING, BANK_OR_CARD_PROBLEM, AMOUNT_TOO_HIGH_RIGHT_NOW, DISPUTES_THE_CHARGE, NO_LONGER_WANTS_THE_ORDER, OTHER.
- **Delay_Reason_Note**: Optional free text accompanying a Delay_Reason. Untrusted, unstructured, non-authorizing input.
- **Hard_Stop_Reason**: The subset of Delay_Reason comprising DISPUTES_THE_CHARGE and NO_LONGER_WANTS_THE_ORDER.
- **Contact_Suppression**: A persisted, non-expiring record that blocks every automated customer-visible action within its declared scope.
- **Suppression_Scope**: The key a Contact_Suppression applies to: the order identifier of the Recovery_Case where the Payment_Event carries one, otherwise the Recovery_Case identifier, in both cases together with the Merchant identifier and the customer key. **[ASSUMPTION]** on including the order identifier.
- **Partial_Arrangement_Request**: A customer's request to settle a Recovery_Case for less than payment_amount, or in instalments. A signal only. No partial money is accepted through Revora.
- **Promise_To_Pay**: A recorded customer statement naming a Promise_Date on which the customer intends to pay payment_amount in full.
- **Promise_Date**: The UTC instant a Promise_To_Pay names.
- **Promise_Status**: The state of a Promise_To_Pay, drawn from RECORDED, FOLLOW_UP_SCHEDULED, KEPT, MISSED, BEYOND_WINDOW_ESCALATED, VOIDED.
- **Follow_Up_Instant**: The UTC instant at which a PROMISE_TO_PAY_FOLLOW_UP becomes eligible for evaluation, computed from Promise_Date and clamped to the Recovery_Window end.
- **Case_Timeline**: The ordered projection of one Recovery_Case's Audit_Records into Timeline_Stages.
- **Timeline_Stage**: One member of the ordered stage sequence DETECTED, DIAGNOSED, BASELINE_ESTIMATED, ALTERNATIVES_PRICED, DECIDED, POLICY_CHECKED, EXECUTED, CUSTOMER_RESPONDED, OUTCOME_VERIFIED.
- **Timeline_Stage_Status**: The status of a Timeline_Stage, drawn from DONE, IN_PROGRESS, UPCOMING, SKIPPED.
- **Reasoning_Call_Kind**: The kind of a permitted Reasoning_Adapter invocation, drawn from exactly CAUSE_HYPOTHESIS, DECISION_EXPLANATION, LINK_DESCRIPTION.
- **Prompt_Contract**: The versioned declaration of the field set a Reasoning_Call_Kind may transmit and the output schema its response must satisfy.
- **Demo_Batch**: A generated set of Recovery_Cases used to demonstrate measured recovery across a batch.
- **Demonstration_Experiment**: An experiment whose inputs originate from a Synthetic_Dataset, reaching the state COMPLETED and reporting a numeric lift with an uncertainty interval.
- **demonstration_incremental_revenue**: The incremental revenue figure of a Demonstration_Experiment, in minor currency units. Distinct from incremental_recovered_revenue and never presented as it.
- **Verified_Demo_Recovery**: A Demo_Batch Recovery_Case that reached RECOVERED from an authoritative Payment_Provider state read against the provider test environment.
- **Null_Action**: A selected Candidate_Action producing no external effect, comprising exactly DO_NOTHING and WAIT. Neither is a Terminal_State and the two remain distinct recorded selections.
- **next_review_at**: The persisted UTC instant at which a Recovery_Case waiting at POLICY_CHECK becomes eligible for re-evaluation. Never later than the Recovery_Window end timestamp.
- **Review_Trigger**: The cause of a re-evaluation of a Recovery_Case waiting at POLICY_CHECK, drawn from exactly SCHEDULED_REVIEW, EVENT_ATTACHED, CUSTOMER_SIGNAL.
- **financial_cost**: The provider fees directly attributable to executing a Candidate_Action, such as a payment-link fee, as an integer count of minor currency units.
- **communication_cost**: The per-message delivery cost of a customer-visible Candidate_Action, such as an SMS or email send fee, as an integer count of minor currency units.
- **total_action_cost**: The sum of financial_cost, communication_cost, risk_cost, and customer_cost for one Candidate_Action, as an integer count of minor currency units. A derived figure, presented alongside its four terms and never in place of them.

## Requirements

### Requirement 18: Customer Access Token Issuance, Scoping, and Expiry

**User Story:** As a Merchant, I want the customer's page reachable from a link in the payment message without a login, and scoped so tightly that the link is worthless for anything except the one payment it was minted for, so that opening the customer side does not open the data.

The base spec has exactly one authentication model: an authenticated Merchant_User session, tenant-scoped by R17.C1 through R17.C3. A customer has no session and never will. This requirement adds a second, deliberately weaker credential and bounds it so narrowly that its compromise costs one case's amount and nothing else. It extends R17.C2 rather than bypassing it: the Merchant identifier still comes from the credential and never from the request.

#### Acceptance Criteria

1. WHEN the Policy_Engine issues an APPROVED Policy_Decision for a customer-visible Candidate_Action on a Recovery_Case that holds no unexpired, unrevoked Customer_Access_Token, THE Customer_Response_Service SHALL mint exactly one Customer_Access_Token for that Recovery_Case before the Execution_Engine issues the external call, carrying the Recovery_Case identifier, the Merchant identifier, an issuance instant, an expiry instant, a token identifier, and a random component holding at least CUSTOMER_TOKEN_ENTROPY_BITS **[ASSUMPTION]** of entropy drawn from a cryptographically secure random source. **[INFERENCE]** — minting must precede the external call because the customer-visible content is what carries the token URL, so a token minted at confirmation would arrive after the only message that could have delivered it.
2. THE Customer_Response_Service SHALL set the expiry instant of a Customer_Access_Token to the earlier of the issuance instant plus CUSTOMER_TOKEN_LIFETIME **[ASSUMPTION]** and the persisted Recovery_Window end timestamp of the Recovery_Case, and SHALL never extend the expiry instant of an issued Customer_Access_Token.
3. THE Customer_Response_Service SHALL persist for a Customer_Access_Token the token identifier, the Recovery_Case identifier, the Merchant identifier, the issuance instant, the expiry instant, the accepted-submission count, and a one-way keyed hash of the token secret, and SHALL persist no reversible copy of the token secret.
4. WHEN the Customer_Response_Service receives a request carrying a Customer_Access_Token, THE Customer_Response_Service SHALL verify the token signature in constant time against the persisted keyed hash, SHALL derive the Recovery_Case identifier and the Merchant identifier from the verified token alone, and SHALL discard any Recovery_Case identifier, Merchant identifier, payment identifier, or amount carried in the request path, query, headers, or body.
5. IF a Customer_Access_Token request names a Recovery_Case identifier other than the one the verified token carries, THEN THE Customer_Response_Service SHALL respond with HTTP status 404, SHALL return no field of any Recovery_Case, and SHALL write an AUTHORIZATION_DENIED Audit_Record carrying the token identifier, the requested Recovery_Case identifier, and the request instant.
6. IF the signature of a presented Customer_Access_Token fails verification, or no persisted token record matches the presented token identifier, THEN THE Customer_Response_Service SHALL respond with HTTP status 404, SHALL return no field of any Recovery_Case, and SHALL write a CUSTOMER_TOKEN_REJECTED Audit_Record recording the rejection category and no part of the presented token.
7. IF a presented Customer_Access_Token verifies but the request instant is at or after the token expiry instant, THEN THE Customer_Response_Service SHALL respond with HTTP status 410, SHALL return no Recovery_Case field other than the expiry indication, and SHALL write a CUSTOMER_TOKEN_EXPIRED Audit_Record. **[ASSUMPTION]** distinguishing 410 from 404 discloses that a token once existed; the disclosure is accepted because CUSTOMER_TOKEN_ENTROPY_BITS makes enumeration infeasible and because a customer holding a dead link needs to be told it is dead.
8. WHEN a Recovery_Case enters a Terminal_State, or a Contact_Suppression covering that Recovery_Case is persisted, THE Customer_Response_Service SHALL mark every Customer_Access_Token of that Recovery_Case revoked with the revocation instant and the revocation reason, and SHALL reject every subsequent request carrying a revoked Customer_Access_Token with HTTP status 410.
9. WHEN the accepted-submission count of a Customer_Access_Token reaches CUSTOMER_TOKEN_MAX_SUBMISSIONS **[ASSUMPTION]**, THE Customer_Response_Service SHALL accept no further Customer_Signal write on that Customer_Access_Token, SHALL continue to serve the read projection until the expiry instant, and SHALL write a CUSTOMER_SUBMISSION_LIMIT_REACHED Audit_Record.
10. THE Customer_Response_Service SHALL treat a Customer_Access_Token as granting read of the Customer_Response_Page projection of exactly one Recovery_Case and write of Customer_Signals for exactly that Recovery_Case, and SHALL grant through a Customer_Access_Token no read of any Audit_Record, any Recommendation, any Policy_Decision, any Metrics_Engine figure, any experiment result, any configuration value, any Merchant_User identifier, and any second Recovery_Case.
11. THE Customer_Response_Service SHALL record the Customer_Access_Token value with the sensitive field kind CUSTOMER_ACCESS_TOKEN, SHALL write no Customer_Access_Token value in clear into any Audit_Record field, any application log record, any error log record, or any diagnostic log record, and SHALL identify a Customer_Access_Token in those records by its token identifier only.
12. WHEN the Customer_Response_Service mints a Customer_Access_Token, THE Audit_Log SHALL persist one CUSTOMER_TOKEN_ISSUED Audit_Record carrying the Recovery_Case identifier, the token identifier, the issuance instant, the expiry instant, and the approved Candidate_Action whose execution the token accompanies, and carrying no part of the token secret.
13. IF a Customer_Access_Token cannot be minted for an approved customer-visible Candidate_Action, THEN THE Execution_Engine SHALL abandon the execution attempt, SHALL issue no Payment_Provider request and no Communication_Provider request, SHALL leave the executed-action counter, the customer-message counter, and the Recovery_Case state unchanged, and THE Audit_Log SHALL persist a CUSTOMER_TOKEN_ISSUE_FAILED Audit_Record naming the failure reason.
14. WHERE a Recovery_Case holds an unexpired, unrevoked Customer_Access_Token at the instant a further customer-visible Candidate_Action is approved, THE Customer_Response_Service SHALL reuse that Customer_Access_Token, SHALL mint no second Customer_Access_Token, and SHALL leave its expiry instant unchanged. **[INFERENCE]** — a second live token for one Recovery_Case doubles the credential surface and buys nothing, since both would grant identical access.

### Requirement 19: Customer Response Page Read Projection and Accepted Writes

**User Story:** As a customer whose payment failed, I want one page that tells me plainly what is owed and lets me say why it is late or when I will pay, so that I am not chased about something I have already explained.

The page is the only surface in Revora a person outside the Merchant sees. Everything it shows is a disclosure decision, so the requirement enumerates both what it presents and what it withholds. The internal economics — probabilities, costs, net value, the alternatives considered — are withheld in full: they are the Merchant's commercial reasoning, and showing a customer that their payment was priced would damage the recovery it is trying to achieve. **[INFERENCE]**

#### Acceptance Criteria

1. WHEN the Customer_Response_Service serves a Customer_Response_Page projection for a verified, unexpired, unrevoked Customer_Access_Token, THE Customer_Response_Service SHALL present the payment_amount of the Recovery_Case formatted from its stored integer minor-currency-unit value, the currency, the configured Merchant display name, the plain-language rendering of the recorded Risk_Cause, the payment link short URL of the live payment link recorded for that Recovery_Case where one exists, the Recovery_Window end timestamp, and the recorded Promise_To_Pay where one exists.
2. THE Customer_Response_Service SHALL present in a Customer_Response_Page projection no customer contact identifier, no payment instrument reference, no second Recovery_Case in any form, no Merchant_User identifier, no Audit_Record, no baseline_recovery_probability, no intervention_recovery_probability, no incremental_probability, no expected_incremental_revenue, no financial_cost, no communication_cost, no risk_cost, no customer_cost, no total_action_cost, no net_recovery_value, no rejected Candidate_Action, no Policy_Decision, and no configuration value.
3. THE Customer_Response_Service SHALL derive every currency figure presented in a Customer_Response_Page projection from the stored integer minor-currency-unit value on the server, and SHALL perform no aggregation, no arithmetic, and no currency re-derivation in the browser client.
4. THE Customer_Response_Service SHALL accept on a Customer_Access_Token exactly three Customer_Signal write shapes: a Delay_Reason with an optional Delay_Reason_Note, a Promise_To_Pay carrying a Promise_Date, and a Partial_Arrangement_Request carrying an optional Delay_Reason_Note, and SHALL reject with HTTP status 422 any write naming a field outside the declared request schema for those three shapes.
5. WHEN the Customer_Response_Service accepts a Customer_Signal, THE Customer_Response_Service SHALL persist exactly one Customer_Signal record carrying the Recovery_Case identifier, the Merchant identifier, the Customer_Signal_Kind, the submission instant as a UTC instant, the token identifier, and the submitted values, SHALL increment the accepted-submission count of the Customer_Access_Token by one, and SHALL persist the Customer_Signal record and the count increment in one atomic transaction that commits both writes or neither.
6. WHEN the Customer_Response_Service persists a Customer_Signal, THE Audit_Log SHALL persist exactly one Audit_Record for that Customer_Signal, within AUDIT_WRITE_TIMEOUT and before the Customer_Response_Service returns a success response, carrying the Customer_Signal_Kind, the submitted values, the token identifier in the actor field, and the correlation_id generated for that submission, extending R11.C1 and R11.C11 to customer-initiated occurrences.
7. WHERE a Recovery_Case already holds MAX_CUSTOMER_SIGNALS_PER_CASE **[ASSUMPTION]** persisted Customer_Signals, THE Customer_Response_Service SHALL reject a further Customer_Signal write with HTTP status 429, SHALL leave every persisted Customer_Signal unchanged, and SHALL write a CUSTOMER_SIGNAL_LIMIT_REACHED Audit_Record.
8. IF a Customer_Signal write arrives for a Recovery_Case already holding a Terminal_State, THEN THE Customer_Response_Service SHALL reject the write with HTTP status 409, SHALL persist no Customer_Signal record, SHALL leave the Recovery_Case state and every Recovery_Case counter unchanged, and SHALL write a CUSTOMER_SIGNAL_REJECTED Audit_Record naming the Terminal_State.
9. THE Customer_Response_Service SHALL cause no Recovery_Case state transition, no Candidate_Action scheduling, no Policy_Engine evaluation, no Payment_Provider request, and no Communication_Provider request to occur inside the request that accepted a Customer_Signal, and SHALL enqueue the consequences of an accepted Customer_Signal for the worker to apply.
10. WHEN a Customer_Signal is enqueued for application, THE Recovery_Case_Manager SHALL apply its consequences through the same legal transition table, the same counters, and the same bounds that govern every other transition (R2.C2, R2.C7, R2.C11), and SHALL reject any consequence that is absent from that table.
11. THE Customer_Response_Service SHALL present the Customer_Response_Page projection with no third-party asset request, no analytics request, and a referrer policy that transmits no referrer, so that the Customer_Access_Token reaches no destination other than the Revora API host.
12. IF the Customer_Response_Service cannot read the Recovery_Case projection within PERSISTENCE_TIMEOUT, THEN THE Customer_Response_Service SHALL respond with HTTP status 503, SHALL return no partial projection, and SHALL accept no Customer_Signal write in that request.

### Requirement 20: Delay Reason Capture As Untrusted, Non-Authorizing Evidence

**User Story:** As a Merchant, I want the customer's stated reason to sharpen the next decision, so that the second contact is not a repeat of the first, and I want it structurally incapable of authorizing anything, so that a text box on a public page cannot move money.

A Delay_Reason is the highest-value evidence in the system and the least trustworthy source in the system, simultaneously. The resolution is the same one the base spec applies to the Reasoning_Layer in R4: the input may inform an estimate, and it may not inform an authorization.

#### Acceptance Criteria

1. THE Customer_Response_Service SHALL accept as a Delay_Reason exactly one member of the enumeration SALARY_OR_CASHFLOW_TIMING, BANK_OR_CARD_PROBLEM, AMOUNT_TOO_HIGH_RIGHT_NOW, DISPUTES_THE_CHARGE, NO_LONGER_WANTS_THE_ORDER, OTHER, and SHALL reject with HTTP status 422 any submission naming a value outside that enumeration.
2. THE Customer_Response_Service SHALL accept an optional Delay_Reason_Note of at most DELAY_NOTE_MAX_LENGTH **[ASSUMPTION]** characters, SHALL truncate a longer submission to that length and mark the stored value TRUNCATED, and SHALL store the note as inert text that is never evaluated, never interpolated into a query, never interpolated into a provider request, and never rendered as markup.
3. THE Revora system SHALL derive no Delay_Reason, no Hard_Stop_Reason, no Promise_Date, no Partial_Arrangement_Request, and no currency figure from the contents of a Delay_Reason_Note.
4. WHEN a Delay_Reason drawn from SALARY_OR_CASHFLOW_TIMING, BANK_OR_CARD_PROBLEM, or AMOUNT_TOO_HIGH_RIGHT_NOW is persisted for a Recovery_Case holding a non-terminal state, THE Diagnosis_Engine SHALL record for the next decision cycle of that Recovery_Case a Diagnosis whose cause is the Risk_Cause the declared Delay_Reason mapping table names, whose method is DETERMINISTIC, whose confidence is CUSTOMER_STATED_CAUSE_CONFIDENCE **[ASSUMPTION]**, and whose evidence names the evidence source CUSTOMER_STATED_REASON together with the Customer_Signal identifier; extending R3.C1 by adding a second deterministic mapping source and R3.C2 by recording a configured confidence in place of 1.0.
5. THE declared Delay_Reason mapping table SHALL map SALARY_OR_CASHFLOW_TIMING to INSUFFICIENT_FUNDS, BANK_OR_CARD_PROBLEM to BANK_OR_NETWORK_FAILURE, AMOUNT_TOO_HIGH_RIGHT_NOW to INSUFFICIENT_FUNDS, and OTHER to no Risk_Cause. **[ASSUMPTION]** on every mapping row; each is a plausible reading of a customer's words rather than a measured correspondence.
6. WHERE the Delay_Reason of a Recovery_Case is OTHER, THE Diagnosis_Engine SHALL leave the Risk_Cause recorded for that Recovery_Case unchanged and SHALL record that the Delay_Reason produced no cause refinement.
7. THE Revora system SHALL configure CUSTOMER_STATED_CAUSE_CONFIDENCE at a value at or above DIAGNOSIS_CONFIDENCE_FLOOR, and SHALL reject a configuration change that sets CUSTOMER_STATED_CAUSE_CONFIDENCE below DIAGNOSIS_CONFIDENCE_FLOOR. **[INFERENCE]** — a customer-stated cause recorded below the floor would substitute to UNKNOWN under R3.C8 and the capture would be inert.
8. THE Policy_Engine SHALL exclude every Delay_Reason value, every Delay_Reason_Note, every Customer_Signal field, and every Promise_To_Pay field other than the persisted Contact_Suppression state from its declared deterministic input set, extending R4.C5, and SHALL derive no policy check outcome and no policy threshold from a Customer_Signal.
9. WHEN a Delay_Reason is persisted for a Recovery_Case, THE Recovery_Case_Manager SHALL leave the Recovery_Window end timestamp, the executed-action counter, the customer-message counter, and the most-recent-outbound-action timestamp of that Recovery_Case unchanged.
10. WHEN the Policy_Engine re-evaluates a recorded Recommendation with every Customer_Signal field of that Recovery_Case removed or replaced while the persisted Contact_Suppression state and the remainder of the declared deterministic input set stay unchanged, THE Policy_Engine SHALL issue the same Policy_Decision verdict, the same primary reason, and the same ordered check outcomes as the originally recorded Policy_Decision.
11. WHERE a Delay_Reason_Note is present and the Prompt_Contract version of the CAUSE_HYPOTHESIS Reasoning_Call_Kind declares the note field, THE Reasoning_Adapter SHALL transmit the note truncated to DELAY_NOTE_MAX_LENGTH and SHALL transmit no customer contact identifier and no payment instrument reference with it, extending R17.C8.
12. THE Merchant_Dashboard SHALL present on the Recovery_Case detail view every persisted Customer_Signal of that Recovery_Case with its Customer_Signal_Kind, its submitted values, its submission instant, and the Delay_Reason_Note where one exists, and SHALL present the note marked as customer-supplied unverified text.

### Requirement 21: Hard-Stop Reasons And Permanent Contact Suppression

**User Story:** As a customer who disputes a charge or no longer wants the order, I want saying so to end the chasing immediately and permanently, so that stating an objection is not the beginning of a longer sequence of messages.

A dispute and a cancellation are not payment problems. They are objections to the debt itself, and continuing automated contact after one is both a customer-harm and a chargeback risk. **[INFERENCE]** Both route to human attention rather than silently stopping, because both have consequences outside Revora — a dispute implies a possible chargeback, a cancellation implies fulfilment and refund questions.

This requirement adds no thirteenth policy check. It writes a Contact_Suppression record that the existing CUSTOMER_OPTED_OUT check (check 5 in the R8.C2 order) already reads as part of its consent-and-opt-out input, so the block happens inside the twelve-check sequence at the position absolute prohibitions already occupy.

#### Acceptance Criteria

1. WHEN a Delay_Reason drawn from the Hard_Stop_Reason subset DISPUTES_THE_CHARGE, NO_LONGER_WANTS_THE_ORDER is persisted for a Recovery_Case, THE Recovery_Case_Manager SHALL persist a Contact_Suppression record carrying the Suppression_Scope, the originating Recovery_Case identifier, the Hard_Stop_Reason, the Customer_Signal identifier, and the suppression instant, in the same atomic transaction as the Customer_Signal record.
2. THE Revora system SHALL retain a persisted Contact_Suppression record with no expiry instant, and SHALL remove or override a Contact_Suppression record only through a recorded configuration change naming an approving Merchant_User, on the same terms R15.C6 applies to a policy rule set change.
3. WHILE a Contact_Suppression record covering the Suppression_Scope of a Recovery_Case exists, THE Policy_Engine SHALL record a non-pass outcome for the CUSTOMER_OPTED_OUT check for every customer-visible Candidate_Action on that Recovery_Case and SHALL issue BLOCKED with the reason CUSTOMER_OPTED_OUT, extending R8.C4 by adding the Contact_Suppression record to that check's input.
4. WHEN a Contact_Suppression record is persisted from the Hard_Stop_Reason DISPUTES_THE_CHARGE, THE Recovery_Case_Manager SHALL transition the Recovery_Case to ESCALATED with the transition reason CUSTOMER_DISPUTED_CHARGE and SHALL record the unresolved payment_amount in minor currency units.
5. WHEN a Contact_Suppression record is persisted from the Hard_Stop_Reason NO_LONGER_WANTS_THE_ORDER, THE Recovery_Case_Manager SHALL transition the Recovery_Case to ESCALATED with the transition reason CUSTOMER_CANCELLED_ORDER and SHALL record the unresolved payment_amount in minor currency units.
6. WHEN a Contact_Suppression record is persisted, THE Execution_Engine SHALL cancel every scheduled and queued Candidate_Action for the covered Recovery_Case for which no execution-intent record exists, SHALL issue no Payment_Provider request and no Communication_Provider request for those cancelled actions, SHALL leave the executed-action counter and the customer-message counter unchanged, and THE Audit_Log SHALL persist one ACTION_CANCELLED_CONTACT_SUPPRESSED Audit_Record per cancelled action.
7. IF an execution-intent record for the covered Recovery_Case already holds ATTEMPTED, CONFIRMED, or UNCERTAIN at the instant a Contact_Suppression record is persisted, THEN THE Execution_Engine SHALL issue no further external call for that Recovery_Case, SHALL resolve that execution-intent record through the reconciliation path of R9.C15, and THE Outcome_Monitor SHALL record the action as POST_SUPPRESSION_ACTION.
8. WHEN a Recovery_Case is created for a payment identifier whose Suppression_Scope holds a Contact_Suppression record, THE Policy_Engine SHALL issue BLOCKED with the reason CUSTOMER_OPTED_OUT for every customer-visible Candidate_Action on that Recovery_Case, irrespective of the recorded Risk_Cause and irrespective of the recorded Recommendation.
9. THE Revora system SHALL apply a Contact_Suppression record without setting the customer-wide opt-out status of R17.C10, and SHALL record the Contact_Suppression scope so that a Merchant_User reading the Recovery_Case can distinguish an objection to one debt from a customer's withdrawal of consent to be contacted at all.
10. WHEN a Contact_Suppression record is persisted, THE Customer_Response_Service SHALL revoke every Customer_Access_Token of the covered Recovery_Case with the revocation reason CONTACT_SUPPRESSED, and SHALL accept no further Customer_Signal write on that Recovery_Case.
11. THE Merchant_Dashboard SHALL present every Recovery_Case holding a Contact_Suppression record in the unresolved-Recovery_Case grouping of R14.C10 under its ESCALATED reason, showing the Hard_Stop_Reason, the suppression instant, and the unresolved payment_amount.
12. WHEN the Outcome_Monitor obtains an authoritative Payment_Provider state read reporting paid or captured for a Recovery_Case holding a Contact_Suppression record, THE Recovery_Case_Manager SHALL reconcile that Recovery_Case to RECOVERED under R10.C14, SHALL leave the Contact_Suppression record in force, and SHALL issue no Payment_Provider request and no Communication_Provider request for that Recovery_Case.

### Requirement 22: Partial Arrangement Request As A Signal, Never As An Accepted Payment

**User Story:** As a Merchant, I want to hear that a customer wants to pay less or pay in instalments, and I want Revora structurally unable to agree to it, so that a negotiation never happens without a person and a partial payment is never reported as a recovery.

Revora has no notion of partial recovery and this feature does not give it one. Payment links keep `accept_partial` false, `partially_paid` keeps its existing treatment as a conflicting payment-state signal that holds the Recovery_Case rather than resolving it, and the definition of recovery stays the full captured amount from an authoritative read. **[FACT]** from the base design and the implemented provider adapter. A Partial_Arrangement_Request is therefore a piece of evidence and a reason to fetch a human, and nothing else.

#### Acceptance Criteria

1. THE Customer_Response_Service SHALL accept a Partial_Arrangement_Request carrying no amount field, no instalment count field, and no schedule field, and SHALL reject with HTTP status 422 a submission carrying any of those fields.
2. WHEN a Partial_Arrangement_Request is persisted for a Recovery_Case, THE Recovery_Case_Manager SHALL transition the Recovery_Case to ESCALATED with the transition reason CUSTOMER_REQUESTED_PARTIAL_ARRANGEMENT and SHALL record the unresolved payment_amount in minor currency units.
3. THE Revora system SHALL issue no Payment_Provider request that sets partial-payment acceptance to true on any payment link, and SHALL create every payment link with partial-payment acceptance false.
4. THE Outcome_Monitor SHALL declare no Recovery_Case RECOVERED on a Payment_Provider state of partially_paid, on a captured amount below the payment_amount of that Recovery_Case, or on any Customer_Signal, and SHALL hold the Recovery_Case as a conflicting payment-state signal under R10.C6 where a partial capture is reported.
5. THE Metrics_Engine SHALL record no partial capture amount in observed_recovered_revenue, in natural_recovered_revenue, in incremental_recovered_revenue, or in demonstration_incremental_revenue, and SHALL record the full payment_amount of a Recovery_Case terminating on CUSTOMER_REQUESTED_PARTIAL_ARRANGEMENT exactly once in unresolved_revenue.
6. WHEN a Partial_Arrangement_Request is persisted, THE Recovery_Memory SHALL persist the request as a feature of the observation for that Recovery_Case under R15.C1, carrying the request instant and the accompanying Delay_Reason_Note where one exists.
7. THE Revora system SHALL leave the payment_amount, the currency, and the Recovery_Window end timestamp of a Recovery_Case unchanged when a Partial_Arrangement_Request is persisted.
8. WHERE a live payment link exists for a Recovery_Case whose Partial_Arrangement_Request was persisted, THE Revora system SHALL leave that payment link live and unmodified for its remaining validity, so that a customer choosing to pay the full amount recovers the Recovery_Case under R10.C14.
9. THE Merchant_Dashboard SHALL present a Recovery_Case terminating on CUSTOMER_REQUESTED_PARTIAL_ARRANGEMENT in the ESCALATED grouping of R14.C10 with the request instant, the accompanying Delay_Reason_Note where one exists, and the unresolved payment_amount.
10. IF a Partial_Arrangement_Request and a Hard_Stop_Reason are persisted for one Recovery_Case, THEN THE Recovery_Case_Manager SHALL apply the Hard_Stop_Reason consequences of Requirement 21 and SHALL record the Partial_Arrangement_Request as a Customer_Signal without a second Terminal_State transition. **[INFERENCE]** — the Hard_Stop_Reason is the stronger statement and the Recovery_Case can hold only one Terminal_State reason.

### Requirement 23: Promise-To-Pay Capture And Recovery Window Clamping

**User Story:** As a customer, I want to say when I will pay and have that respected, so that I am contacted once around that date rather than repeatedly before it.

A promise changes *when* Revora acts and never *how long* Revora may act. The Recovery_Window is set at case creation and never extended (R2.C5); that immutability is what makes R2.C12's termination bound provable, and a promise that could extend it would remove the guarantee. A promised date beyond the window end is therefore not a scheduling problem to be solved by stretching the window; it is a case for a person. **[INFERENCE]**

#### Acceptance Criteria

1. THE Customer_Response_Service SHALL accept a Promise_To_Pay carrying exactly one Promise_Date expressed as an instant, SHALL convert that instant to UTC before persistence, and SHALL retain the received representation alongside the persisted Promise_To_Pay, on the same terms R16.C13 applies to a Payment_Event timestamp.
2. IF a submitted Promise_Date is earlier than the submission instant plus PROMISE_MIN_LEAD_TIME **[ASSUMPTION]**, THEN THE Customer_Response_Service SHALL reject the submission with HTTP status 422, SHALL persist no Promise_To_Pay, and SHALL write a PROMISE_REJECTED Audit_Record naming the lead-time rule.
3. WHEN a Promise_To_Pay whose Promise_Date is earlier than the persisted Recovery_Window end timestamp is accepted for a Recovery_Case, THE Recovery_Case_Manager SHALL persist the Promise_To_Pay with the Promise_Status RECORDED and SHALL compute the Follow_Up_Instant as the earlier of the Promise_Date plus PROMISE_FOLLOW_UP_OFFSET **[ASSUMPTION]** and the Recovery_Window end timestamp minus PROMISE_WINDOW_SAFETY_MARGIN **[ASSUMPTION]**.
4. THE Recovery_Case_Manager SHALL leave the persisted Recovery_Window end timestamp of a Recovery_Case unchanged when a Promise_To_Pay is persisted, when a Follow_Up_Instant is computed, when a Promise_Status changes, and when a PROMISE_TO_PAY_FOLLOW_UP executes.
5. IF a submitted Promise_Date is at or after the persisted Recovery_Window end timestamp, THEN THE Recovery_Case_Manager SHALL persist the Promise_To_Pay with the Promise_Status BEYOND_WINDOW_ESCALATED, SHALL compute no Follow_Up_Instant, SHALL schedule no PROMISE_TO_PAY_FOLLOW_UP, and SHALL transition the Recovery_Case to ESCALATED with the transition reason PROMISE_BEYOND_RECOVERY_WINDOW recording the unresolved payment_amount and the submitted Promise_Date.
6. IF the Follow_Up_Instant computed under criterion 3 is earlier than the submission instant, THEN THE Recovery_Case_Manager SHALL persist the Promise_To_Pay with the Promise_Status BEYOND_WINDOW_ESCALATED and SHALL transition the Recovery_Case to ESCALATED with the transition reason PROMISE_BEYOND_RECOVERY_WINDOW. **[INFERENCE]** — a window whose remaining time is shorter than PROMISE_WINDOW_SAFETY_MARGIN admits no follow-up inside it.
7. WHERE a Recovery_Case already holds MAX_PROMISES_PER_CASE **[ASSUMPTION]** persisted Promise_To_Pay records, THE Customer_Response_Service SHALL reject a further Promise_To_Pay submission with HTTP status 409, SHALL leave the persisted Promise_To_Pay and its Promise_Status unchanged, SHALL persist the submission as a Customer_Signal for Recovery_Memory, and SHALL write a PROMISE_ALREADY_RECORDED Audit_Record.
8. WHEN a Promise_To_Pay is persisted with the Promise_Status RECORDED, THE Audit_Log SHALL persist one PROMISE_RECORDED Audit_Record carrying the Promise_Date, the computed Follow_Up_Instant, the Recovery_Window end timestamp, and the token identifier in the actor field, so that a reader can check the clamp from the audit trail alone.
9. WHILE a Promise_To_Pay holds the Promise_Status RECORDED and the current instant is earlier than the Follow_Up_Instant, THE Value_Optimizer SHALL exclude PROMISE_TO_PAY_FOLLOW_UP from selection with the exclusion reason PROMISE_DATE_NOT_REACHED and SHALL retain the excluded Candidate_Action in the recorded Recommendation.
10. WHEN an authoritative Payment_Provider state read reports paid or captured for a Recovery_Case holding a Promise_To_Pay, THE Recovery_Case_Manager SHALL set the Promise_Status to KEPT and SHALL record the interval in seconds between the Promise_Date and the provider-reported payment timestamp.
11. WHEN a PROMISE_TO_PAY_FOLLOW_UP execution-intent record for a Recovery_Case reaches CONFIRMED and a subsequent authoritative Payment_Provider state read reports a payment state other than paid or captured, THE Recovery_Case_Manager SHALL set the Promise_Status to MISSED and SHALL record the missed-promise instant.
12. WHEN a Recovery_Case holding a Promise_To_Pay with the Promise_Status RECORDED reaches a Terminal_State other than RECOVERED, THE Recovery_Case_Manager SHALL set the Promise_Status to VOIDED and SHALL record the Terminal_State that voided it.
13. THE Recovery_Case_Manager SHALL evaluate every Promise_To_Pay holding the Promise_Status RECORDED or FOLLOW_UP_SCHEDULED at least once per PROMISE_SWEEP_INTERVAL **[ASSUMPTION]**, and SHALL apply any reached Follow_Up_Instant, elapsed Recovery_Window, or elapsed Cooldown detected by that evaluation within the same evaluation.
14. THE Merchant_Dashboard SHALL present on the Recovery_Case detail view the Promise_Date, the Promise_Status, the computed Follow_Up_Instant, and the Recovery_Window end timestamp of every persisted Promise_To_Pay, and SHALL present the Recovery_Window end timestamp adjacent to the Promise_Date so that a clamped Follow_Up_Instant is visible as a clamp.

### Requirement 24: PROMISE_TO_PAY_FOLLOW_UP As An Executable, Priced, Exactly-Once Action

**User Story:** As a Merchant, I want the promise follow-up to be a real action that competes for selection on its own economics, so that following up on a promise is chosen when it is worth more than doing nothing and skipped when it is not.

`PROMISE_TO_PAY_FOLLOW_UP` currently sits in the candidate vocabulary marked unavailable, absent from every cause-to-action eligibility row, so it never produces an estimate. **[FACT]** from the implemented action module. This requirement makes it executable without exempting it from anything: it is priced like every other action, ranked by net_recovery_value like every other action, gated by all twelve policy checks like every other action, and executed through the same execution-intent and Idempotency_Key mechanism of R9.C3 through R9.C6.

The external effect is a Payment_Provider notification against the live payment link already recorded for the Recovery_Case, or, where no live payment link exists, a new payment link with notification enabled. Whether the Payment_Provider exposes a re-notification capability that does not create a second link is **[EVIDENCE INSUFFICIENT]** and must be verified before design closes; the requirement is written against a generic capability so a verified alternative substitutes without a rewrite.

#### Acceptance Criteria

1. THE Revora system SHALL treat PROMISE_TO_PAY_FOLLOW_UP as an executable Candidate_Action, as a Candidate_Action requiring a Payment_Provider call, and as a customer-visible Candidate_Action that consumes MAX_CUSTOMER_MESSAGES.
2. THE Intervention_Simulator SHALL include PROMISE_TO_PAY_FOLLOW_UP in the Candidate_Action set of a Recovery_Case only where a Promise_To_Pay holding the Promise_Status RECORDED or FOLLOW_UP_SCHEDULED exists for that Recovery_Case, and SHALL otherwise record the exclusion reason NO_PROMISE_RECORDED while retaining the excluded Candidate_Action in the recorded set.
3. THE declared cause-to-action eligibility table SHALL permit PROMISE_TO_PAY_FOLLOW_UP for every Risk_Cause other than FRAUD_OR_RISK_SIGNAL and UNKNOWN, and SHALL record the exclusion reason CAUSE_NOT_ELIGIBLE where the recorded Risk_Cause is FRAUD_OR_RISK_SIGNAL or UNKNOWN. **[INFERENCE]** — a rejected or low-confidence diagnosis must keep making Revora more conservative, which R3.C8 achieves by substituting UNKNOWN.
4. WHEN the Intervention_Simulator includes PROMISE_TO_PAY_FOLLOW_UP in a Candidate_Action set, THE Intervention_Simulator SHALL produce a financial_cost equal to PROMISE_FOLLOW_UP_FINANCIAL_COST **[ASSUMPTION]**, a communication_cost equal to PROMISE_FOLLOW_UP_COMMUNICATION_COST **[ASSUMPTION]**, a risk_cost, a customer_cost, and an intervention_recovery_probability, each currency figure an integer count of minor currency units, leaving none of the five figures unset.
5. WHERE Recovery_Memory holds fewer than MIN_SEGMENT_SAMPLE_SIZE observations of PROMISE_TO_PAY_FOLLOW_UP for the feature segment of a Recovery_Case, THE Intervention_Simulator SHALL produce the intervention_recovery_probability PROMISE_FOLLOW_UP_PRIOR_PROBABILITY **[ASSUMPTION]** marked with the estimation method UNCALIBRATED, and SHALL retain the Candidate_Action in the Candidate_Action set.
6. THE Value_Optimizer SHALL rank PROMISE_TO_PAY_FOLLOW_UP by net_recovery_value on the same terms as every other Candidate_Action, SHALL apply MIN_NET_VALUE_THRESHOLD, MIN_INCREMENTAL_PROBABILITY, and MAX_COST_TO_VALUE_RATIO to it unchanged, and SHALL take no ranking input from the existence of a Promise_To_Pay.
7. WHEN the Value_Optimizer selects PROMISE_TO_PAY_FOLLOW_UP for a Recovery_Case, THE Policy_Engine SHALL evaluate that selection against all twelve ordered checks of R8.C2 and SHALL issue no APPROVED Policy_Decision where any check returns a non-pass or UNAVAILABLE outcome.
8. IF the Follow_Up_Instant of a Recovery_Case falls earlier than the most-recent-outbound-action timestamp plus COOLDOWN_INTERVAL, THEN THE Policy_Engine SHALL issue DEFERRED with the reason COOLDOWN_ACTIVE and an earliest permitted execution timestamp equal to that most-recent-outbound-action timestamp plus COOLDOWN_INTERVAL, and SHALL issue BLOCKED with the reason WINDOW_EXPIRED in place of DEFERRED where that earliest permitted execution timestamp falls at or after the Recovery_Window end timestamp, applying R8.C8 unchanged.
9. WHEN the Execution_Engine executes an approved PROMISE_TO_PAY_FOLLOW_UP, THE Execution_Engine SHALL derive the Idempotency_Key deterministically from the Recovery_Case identifier, the Candidate_Action type PROMISE_TO_PAY_FOLLOW_UP, and the attempt ordinal, SHALL persist an execution-intent record carrying that Idempotency_Key in the state ATTEMPTED, and SHALL issue the external call only after that record is durably committed, applying R9.C3 and R9.C4 unchanged.
10. WHEN the Execution_Engine executes an approved PROMISE_TO_PAY_FOLLOW_UP for a Recovery_Case holding a live payment link, THE Execution_Engine SHALL issue a Payment_Provider notification against that recorded payment link, SHALL create no second payment link for that Recovery_Case, and SHALL persist the provider-supplied response identifier with the state CONFIRMED on the execution-intent record. **[EVIDENCE INSUFFICIENT]** on the provider re-notification capability.
11. WHERE no live payment link exists for a Recovery_Case whose PROMISE_TO_PAY_FOLLOW_UP is approved, THE Execution_Engine SHALL create one payment link with partial-payment acceptance false, with an expiry clamped to the Recovery_Window end timestamp, and with notification enabled, and SHALL treat that creation as the external effect of that Idempotency_Key.
12. WHEN a PROMISE_TO_PAY_FOLLOW_UP execution-intent record reaches CONFIRMED, THE Recovery_Case_Manager SHALL increment the executed-action counter exactly once for that Idempotency_Key, SHALL increment the customer-message counter exactly once for that Idempotency_Key, SHALL set the most-recent-outbound-action timestamp to the confirmation timestamp, SHALL set the Promise_Status to FOLLOW_UP_SCHEDULED, and SHALL transition the Recovery_Case to WAITING_FOR_OUTCOME.
13. WHEN a PROMISE_TO_PAY_FOLLOW_UP reaches its Follow_Up_Instant, THE Recovery_Case_Manager SHALL enqueue exactly one decision cycle for that Recovery_Case within PROMISE_SWEEP_INTERVAL of that instant, SHALL apply the decision-cycle counter bound of R2.C14 to that cycle, and SHALL transition the Recovery_Case to STOPPED with the transition reason DECISION_CYCLE_LIMIT_REACHED where the decision-cycle counter has reached MAX_RECOVERY_ATTEMPTS.
14. WHEN a Promise_Status is set to MISSED, THE Recovery_Case_Manager SHALL apply the remaining Recovery_Window, MAX_RECOVERY_ATTEMPTS, MAX_CUSTOMER_MESSAGES, COOLDOWN_INTERVAL, and decision-cycle bounds unchanged, SHALL return the Recovery_Case to DECISION_PENDING where every bound still permits a further action, and SHALL transition the Recovery_Case to STOPPED otherwise.
15. THE Revora system SHALL execute across the whole lifetime of one Recovery_Case no more than MAX_RECOVERY_ATTEMPTS outbound actions and no more than MAX_CUSTOMER_MESSAGES customer-visible actions counting every PROMISE_TO_PAY_FOLLOW_UP among them, and SHALL cause every Recovery_Case holding a Promise_To_Pay to reach a Terminal_State within the bound of R2.C12.
16. WHERE the Payment_Provider re-notification capability is not confirmed by design-phase verification, THE Intervention_Simulator SHALL mark PROMISE_TO_PAY_FOLLOW_UP UNAVAILABLE with the exclusion reason PROVIDER_CAPABILITY_UNVERIFIED, SHALL exclude it from selection, and SHALL retain it in the recorded Candidate_Action set, applying R6.C9 unchanged.
17. WHERE Revora authors the content of a customer-visible Candidate_Action, THE Execution_Engine SHALL carry the Customer_Response_Page URL of the Recovery_Case as the single Policy_Engine-approved link and SHALL carry no second link, and WHERE the external effect is a Payment_Provider notification whose content the Payment_Provider authors, THE Execution_Engine SHALL record that execution with the classification PROVIDER_HOSTED_LINK_NOTIFICATION and THE Audit_Log SHALL persist that classification, so that a reader can distinguish content Revora controlled from content it did not. **[EVIDENCE INSUFFICIENT]** on whether the Payment_Provider permits Revora-authored content on a re-notification.

### Requirement 25: Customer Signals In Recovery Memory And The Next Decision Cycle

**User Story:** As a Merchant, I want what a customer told us to change what Revora estimates next time, and I want it structurally unable to change what Revora is allowed to do, so that learning from customers does not become a way for customers to move the limits.

R15.C6 already forbids the Policy_Engine from deriving any check or threshold from Recovery_Memory. This requirement puts Customer_Signals inside Recovery_Memory, which means that prohibition covers them automatically, and states the coverage explicitly rather than leaving it implied. **[INFERENCE]**

#### Acceptance Criteria

1. WHEN the Recovery_Case_Manager records a Recovery_Case transition to a Terminal_State, THE Recovery_Memory SHALL persist on the observation for that Recovery_Case the recorded Delay_Reason where one exists, the Promise_Status where a Promise_To_Pay exists, the interval in seconds between the Promise_Date and the Recovery_Case outcome instant where both exist, an indication of whether a Partial_Arrangement_Request was persisted, an indication of whether a Contact_Suppression record covers the Recovery_Case, and the count of persisted Customer_Signals, in the same atomic transaction R15.C1 requires.
2. THE Recovery_Memory SHALL record the data provenance value REAL for a Customer_Signal originating from a Customer_Response_Page submission and the data provenance value SYNTHETIC for a Customer_Signal originating from a Synthetic_Dataset, applying R15.C2 unchanged.
3. THE Recovery_Memory SHALL store the Delay_Reason and the Promise_Status as feature values available to the Baseline_Model and the Intervention_Simulator for feature segmentation, and SHALL make the observations carrying each Delay_Reason value selectable as a distinct segment.
4. THE Baseline_Model SHALL derive its training labels only from observations carrying the intervention-status value NO_INTERVENTION_CONFIRMED, applying R5.C6 unchanged, and SHALL treat an observation carrying a Customer_Signal that arrived after a Revora action as REVORA_INTERVENED. **[INFERENCE]** — a customer who responded to a message Revora sent is not a no-intervention observation.
5. WHEN a Delay_Reason is persisted for a Recovery_Case in a non-terminal state, THE Value_Optimizer SHALL construct the Candidate_Action set of the next decision cycle of that Recovery_Case from the Risk_Cause recorded under R20.C4, and SHALL record in the Recommendation the Customer_Signal identifier that produced that Risk_Cause.

### Requirement 30: Re-Evaluation Of A Recovery Case That Chose Restraint

**User Story:** As a Merchant, I want a case where Revora correctly decided to wait to be looked at again — on a schedule, when a new failure arrives, and when the customer says something — so that choosing restraint is a decision to revisit rather than a decision to abandon.

**The verified defect this requirement fixes.** The implemented transition table declares exactly two edges into DECISION_PENDING: DIAGNOSED → DECISION_PENDING and WAITING_FOR_OUTCOME → DECISION_PENDING. There is no POLICY_CHECK → DECISION_PENDING edge. **[FACT]** from `revora/domain/transitions.py`. The consequences compound:

- When the Value_Optimizer selects a Null_Action, the pipeline leaves the Recovery_Case at POLICY_CHECK — non-terminal, which is correct — but no mechanism can begin a second decision cycle for it. The lifecycle sweep only ever transitions such a Recovery_Case to EXPIRED. **[FACT]** from `revora/jobs/pipeline.py` and `revora/cases/sweeper.py`.
- Attaching a subsequent at-risk Payment_Event to an already-open Recovery_Case writes an EVENT_ATTACHED_TO_CASE Audit_Record and changes nothing else. It enqueues no decision cycle. **[FACT]** from `revora/detection/service.py`.
- WAIT is therefore behaviourally identical to abandoning the Recovery_Case until its Recovery_Window elapses. **[INFERENCE]**
- The worst consequence, named because it is the reason this requirement is load-bearing: reaching WAITING_FOR_OUTCOME requires a confirmed executed action, so the only re-entry loop that exists is reachable only after an intervention. **Revora currently re-decides only the Recovery_Cases it already intervened on.** A Recovery_Case where it correctly chose restraint never gets a second look. That is a systematic bias against the product's own objective of intervening only when intervention is worth more than waiting. **[INFERENCE]**

The fix adds one transition edge, one persisted instant, one periodic sweep, and two event-driven triggers. It adds no new bound category and removes no existing one: the new loop increments the same decision-cycle counter the two existing edges into DECISION_PENDING increment, so MAX_RECOVERY_ATTEMPTS and the decision-cycle cap of R2.C14 bound it exactly as they bound the existing loop, and the Recovery_Window end timestamp stays immutable, so R2.C12's termination bound is preserved rather than weakened.

#### Acceptance Criteria

1. THE declared legal transition table SHALL hold the edge POLICY_CHECK → DECISION_PENDING with the transition kind REVIEW and the counter effect decision_cycle_delta of 1, SHALL leave the executed-action counter, the customer-message counter, and the most-recent-outbound-action timestamp unchanged on that edge, and SHALL reject a POLICY_CHECK → DECISION_PENDING transition absent from that table on the same terms R2.C2 applies to every other transition.
2. THE Recovery_Case_Manager SHALL leave the persisted Recovery_Window end timestamp of a Recovery_Case unchanged when a review is scheduled, when a review is triggered, when a POLICY_CHECK → DECISION_PENDING transition is applied, and when a review re-selects a Null_Action, so that the termination bound of R2.C12 holds for any number of reviews of any kind.
3. WHEN the Value_Optimizer selects a Null_Action for a Recovery_Case and the Policy_Engine records that selection, THE Recovery_Case_Manager SHALL persist on that Recovery_Case a next_review_at instant equal to the earlier of the selection instant plus WAIT_REVIEW_INTERVAL **[ASSUMPTION]** and the persisted Recovery_Window end timestamp, and SHALL persist no next_review_at instant later than that Recovery_Window end timestamp.
4. WHEN a Recovery_Case leaves the state POLICY_CHECK for any reason, THE Recovery_Case_Manager SHALL clear the persisted next_review_at instant of that Recovery_Case in the same atomic transaction as the state transition.
5. THE Review_Sweeper SHALL visit at least once per REVIEW_SWEEP_INTERVAL **[ASSUMPTION]** every Recovery_Case holding the state POLICY_CHECK whose persisted next_review_at instant is at or before the current instant and whose decision-cycle counter is below MAX_RECOVERY_ATTEMPTS, and SHALL enqueue exactly one decision cycle for each such Recovery_Case.
6. THE Review_Sweeper SHALL determine every Recovery_Case it visits from persisted Recovery_Case fields and persisted timestamps alone, and SHALL identify and act on every eligible Recovery_Case after a process restart that begins with an empty job queue, on the same terms R2.C13 requires of the lifecycle evaluation sweep.
7. WHEN an at-risk Payment_Event attaches to an already-open Recovery_Case holding the state POLICY_CHECK, THE Detection_Service SHALL enqueue exactly one decision cycle for that Recovery_Case in the same atomic transaction as the attach and the EVENT_ATTACHED_TO_CASE Audit_Record, SHALL leave the persisted payment_amount and the persisted detection timestamp of that Recovery_Case unchanged, and SHALL create no second Recovery_Case for that payment identifier, applying R1.C10 unchanged.
8. WHEN the Customer_Response_Service accepts a Customer_Signal for a Recovery_Case holding the state POLICY_CHECK, THE Customer_Response_Service SHALL enqueue exactly one decision cycle for that Recovery_Case for the worker to apply, SHALL apply no state transition inside the accepting request, and SHALL cause no Policy_Engine evaluation inside the accepting request, applying R19.C9 unchanged.

### Requirement 31: Four-Term Cost Decomposition

**User Story:** As a Merchant, I want to see which kind of cost made an action not worth taking, so that I can tell a provider fee I could renegotiate from a customer-friction penalty I chose.

The implemented Intervention_Simulator produces three cost figures — `action_cost`, `risk_cost`, `customer_cost` — with provider fees and per-message delivery cost blended into `action_cost`. **[FACT]** Blending them means an exclusion under MAX_COST_TO_VALUE_RATIO cannot be attributed to a cause: a payment link excluded because links are expensive and a payment link excluded because messages are expensive present identically. This requirement splits `action_cost` into `financial_cost` and `communication_cost` and changes nothing else about how a decision is reached.

The split is a decomposition and a presentation change. It must not change which Candidate_Action is selected for any input whose blended total is unchanged, and criterion 8 states that as a testable obligation rather than as an intention.

#### Acceptance Criteria

1. THE Intervention_Simulator SHALL produce for every Candidate_Action a financial_cost and a communication_cost as two separately estimated, separately persisted integer counts of minor currency units in place of a single action_cost, and SHALL persist no action_cost field on a Candidate_Action estimate produced after this requirement is in force.
2. THE Intervention_Simulator SHALL estimate financial_cost as the provider fees directly attributable to executing that Candidate_Action, SHALL estimate communication_cost as the per-message delivery cost of that Candidate_Action, and SHALL produce a communication_cost of zero for a Candidate_Action that is not customer-visible.
3. THE Value_Optimizer SHALL compute net_recovery_value as expected_incremental_revenue minus financial_cost minus communication_cost minus risk_cost minus customer_cost, SHALL perform that arithmetic in integer minor currency units at every step, and SHALL round exactly once, at the single multiplication of a probability into a money figure, applying R7.C12 unchanged.
4. THE Value_Optimizer SHALL compute the total cost of a Candidate_Action for every exclusion rule that references total cost, including the MAX_COST_TO_VALUE_RATIO rule of R7.C4, as the sum of financial_cost, communication_cost, risk_cost, and customer_cost, and SHALL apply the exclusion reason NON_POSITIVE_INCREMENTAL_VALUE before performing any cost-to-value division, preserving the ordering guarantee of R7.C4 unchanged.
5. THE Intervention_Simulator SHALL record an estimation method label for financial_cost and for communication_cost drawn from the same enumeration the existing three cost figures use — DETERMINISTIC, PRIOR_FALLBACK, UNCALIBRATED, DEFINITIONAL — and SHALL leave neither label unset.
6. THE Intervention_Simulator SHALL produce for DO_NOTHING a financial_cost of zero, a communication_cost of zero, a risk_cost of zero, and a customer_cost of zero, each with the estimation method DEFINITIONAL, and THE Value_Optimizer SHALL compute the net_recovery_value of DO_NOTHING as exactly zero.
7. THE Merchant_Dashboard SHALL present on the Recovery_Case detail view and THE Timeline_Reader SHALL present at the ALTERNATIVES_PRICED and DECIDED Timeline_Stages the financial_cost, the communication_cost, the risk_cost, and the customer_cost of a Candidate_Action as four separate figures, SHALL present total_action_cost alongside those four figures, and SHALL present total_action_cost in place of none of them.
8. THE Value_Optimizer SHALL select the same Candidate_Action, record the same exclusion reason for every excluded Candidate_Action, and compute the same net_recovery_value for every Candidate_Action as the pre-split implementation computed, for any input whose financial_cost plus communication_cost equals the pre-split action_cost and whose risk_cost and customer_cost are unchanged.
9. WHEN a persisted Candidate_Action estimate holding an action_cost is migrated, THE Revora system SHALL set financial_cost to the persisted action_cost value, SHALL set communication_cost to zero, and SHALL mark that row with the estimation method COST_SPLIT_NOT_MEASURED for both figures, and SHALL derive no split of a migrated action_cost from any inference about the Candidate_Action type. **[INFERENCE]** — fabricating a plausible-looking split on historical rows would present a guess as a measurement, which is the failure the provenance labelling of the base spec exists to prevent.
10. THE Merchant_Dashboard SHALL present a Candidate_Action estimate marked COST_SPLIT_NOT_MEASURED with that marking adjacent to its financial_cost and communication_cost figures, so that a reader does not read a migrated zero as a measured zero.
11. THE Revora system SHALL hold PAYMENT_LINK_FINANCIAL_COST and MESSAGE_COMMUNICATION_COST as versioned configuration rows changeable only through a recorded configuration change naming an approving Merchant_User, on the same terms R15.C6 applies to every other bound, and SHALL hold neither as a code constant and neither as an environment variable.
12. THE Metrics_Engine SHALL report cost per recovery from the sum of the four cost terms of every confirmed executed Candidate_Action in the reporting period, SHALL report the four terms separately alongside that sum, and SHALL report every figure as an integer count of minor currency units.

### Deferred, Not Silently Included

- Partial payment acceptance of any kind. Payment links keep partial-payment acceptance false and Revora keeps no notion of partial recovery.
- Instalment plans, settlement negotiation, and any automated response to a Partial_Arrangement_Request beyond escalation to a human.
- A second Promise_To_Pay per Recovery_Case, and any re-promise after a MISSED promise. MAX_PROMISES_PER_CASE is 1.
- Recovery_Window extension by any mechanism. The window stays immutable after case creation.
- Customer authentication of any kind: no login, no session, no one-time password, no identity verification. The Customer_Access_Token is a bearer capability and nothing more.
- Any customer-side channel other than the web page: no inbound SMS parsing, no inbound email parsing, no voice, no chat.
- Free-text interpretation as a source of structured facts. A Delay_Reason_Note never yields a Delay_Reason, a Promise_Date, an amount, or a Hard_Stop_Reason.
- Reasoning_Adapter use beyond the three declared Reasoning_Call_Kinds: no tool use, no agent loop, no autonomous action selection, no retrieval-augmented generation, no model-authored policy.
- Model fine-tuning, model retraining, and automated model promotion. Promotion stays a recorded human act under R15.C5.
- A thirteenth policy check. Contact_Suppression enters the existing CUSTOMER_OPTED_OUT check's input rather than adding a check.
- Customer-wide opt-out from a Hard_Stop_Reason. A hard stop is scoped to the Suppression_Scope; withdrawing consent to be contacted at all stays a separate, explicitly recorded act under R17.C10.
- A real-traffic experiment and any Attributed_Recovery claim. The Demonstration_Experiment is synthetic and labelled as such.
- Multi-currency. One currency per Merchant, unchanged from the base spec.
- Any additional decision-cycle budget for the review loop of Requirement 30. Reviews consume the same MAX_RECOVERY_ATTEMPTS and the same decision-cycle cap as every other cycle; no separate review allowance exists.
- Any review of a Recovery_Case holding a Terminal_State. Requirement 30 applies to POLICY_CHECK only, and the reconciliation edge of the base spec stays the only route out of a Terminal_State.
- Renaming any implemented enumeration member. DO_NOTHING and WAIT stay distinct, CUSTOMER_MESSAGE keeps its name, and STOPPED, BLOCKED, and EXPIRED stay three Terminal_States. Only the presented labels change, under R26.C14.
- RETRY and DELAYED_RETRY as executable actions. No provider capability exists to retry a failed one-off payment; both stay UNAVAILABLE and stay visible in the recorded Candidate_Action set.
- Any further cost decomposition beyond the four terms of Requirement 31, and any per-channel cost breakdown within communication_cost.
- Any reconstruction of a measured financial and communication split for historical Candidate_Action estimates. Migrated rows are marked COST_SPLIT_NOT_MEASURED and left that way.

### Items Requiring Verification Before Design Closes

Each is **[EVIDENCE INSUFFICIENT]** at requirements time.

1. Whether the Payment_Provider exposes a way to re-notify a customer about an already-created payment link without creating a second link, and the idempotency semantics of that capability. Requirement 24 depends on it; R24.C16 is the fallback where it is absent.
2. The Payment_Provider notification cost per message, which PROMISE_FOLLOW_UP_ACTION_COST currently guesses at 50 minor units.
3. Whether a customer-stated reason correlates with recovery outcome at all, and at what strength. CUSTOMER_STATED_CAUSE_CONFIDENCE is a placeholder, and every row of the Delay_Reason mapping table is a plausible reading rather than a measured correspondence.
4. The real base rate of promise-keeping, which PROMISE_FOLLOW_UP_PRIOR_PROBABILITY currently guesses at 0.45.
5. Applicable statutory and contractual obligations covering a page that displays a debt to an unauthenticated holder of a URL, and covering the retention of a customer's free-text explanation.
6. Whether disclosing token expiry through HTTP status 410 while disclosing nothing else is acceptable under the applicable obligations of item 5.
7. Model provider rate limits, per-request cost, and latency distribution for the configured model at the configured region, against which REASONING_TIMEOUT and MAX_REASONING_CALLS_PER_CASE were set without measurement.
8. Whether the configured model returns schema-conformant structured output reliably enough that REJECTED_AI_OUTPUT stays a rare path rather than the common one.
9. The permitted origin set for the Customer_Response_Page under the deployment assumption, which determines whether the cross-origin control of R29.C8 is enforceable as stated.
10. Whether the deployment assumption recorded in the introduction holds: specifically, whether the chosen container host provides a scheduler with a period at or below the smaller of PROMISE_SWEEP_INTERVAL and REVIEW_SWEEP_INTERVAL.
11. The real per-link financial cost the Payment_Provider charges, which PAYMENT_LINK_FINANCIAL_COST currently guesses at 300 minor units, and the real per-message communication cost, which MESSAGE_COMMUNICATION_COST currently guesses at 25 minor units. Both feed every net_recovery_value comparison, so both change which actions are selected.
12. Whether PROMISE_FOLLOW_UP_FINANCIAL_COST of zero holds, which depends on verification item 1: a re-notification against an existing payment link incurs no new link fee only if the capability exists.
13. Whether WAIT_REVIEW_INTERVAL at 12 hours is appropriate against real customer behaviour. Too short wastes decision cycles on unchanged evidence; too long lets the Recovery_Window elapse with reviews unspent. The interval was chosen without measurement.
14. The conversion cost of the recorded Shape B decision — the fraction of recipients who pay through a payment link reached directly but do not pay through one reached via the Customer_Response_Page. Unmeasured.
